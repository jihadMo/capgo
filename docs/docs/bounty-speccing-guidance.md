# SatCode Bounty Speccing Guidance

Best practices for creators to write clear, reproducible, and winnable bounty specifications.

## 1. Structure of an Effective Bounty Spec
Every bounty created on SatCode should contain:
- **Summary**: Concise 1-2 sentence description of the problem or feature.
- **Acceptance Criteria**: Bulleted, testable checklist of what "done" looks like.
- **Technical Context**: Relevant file paths, architectural guidance, and accepted tech stack.
- **Verification Plan**: Step-by-step instructions for testing (unit tests, manual repro steps).

## 2. Best Practices for Creators
- **Keep Scope Tight**: Focus on a single bug or component. Avoid multi-month mega-tasks.
- **Define Objective Criteria**: State exact status codes, type schemas, or UI behaviors expected.
- **Provide Repro Steps**: Include sample cURL commands or test input payloads.
- **Set Fair Payout Rules**: Payout is released upon PR merge after code review.
